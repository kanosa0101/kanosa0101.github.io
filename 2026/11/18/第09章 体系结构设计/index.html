9.1 软件体系结构（第 5–10 页）

软件体系结构（Software Architecture，架构）是软件系统的一个或多个结构。每个结构描述构件、构件的外部可见属性及构件间的相互关系。例如，外部可见属性包括构件提供的服务和接口，关系可以表现为调用、信息传递或依赖。

体系结构帮助团队分析设计能否满足需求、在变更代价较低时比较候选方案、降低软件构造风险。一个规模较小、便于理解的架构模型还能支持利益相关者交流，明确影响后续开发的早期决策，并展示各构件怎样协作（第 5、7 页）。

课件用「类与对象」来解释架构和具体设计的关系。具体设计体现了架构的选择。同一个客户机—服务器架构可以用不同平台、构件和接口实现，例如课件中的 Java EE 与 .NET 方案（第 6 页）。

体系结构描述用不同的视图回答不同利益相关者的关注点。例如，开发人员关心子系统职责和接口，部署人员关心软件元素如何分布在运行节点上。选用什么视图取决于要回答的问题（第 8 页）。记录架构选择可使用体系结构决策模板（第 9–10 页）。

9.2 敏捷性与体系结构（第 12 页）

敏捷团队需要随新需求调整，架构设计师需要对重要结构进行斟酌并征求利益相关者意见。课件介绍进展的签署。每完成一轮新原型，就记录该轮工作产品和关键架构决定，由相关人员确认。这样可以在迭代中持续复核重要设计。

9.3 体系结构风格（第 14–24 页）

五种体系结构风格（第 14–22 页）

体系结构风格给出一类系统常用的构件组织和交互方式。判断风格时看构件主要凭什么协作。

风格 构件怎样协作 特点与限制
以数据为中心的体系结构（仓库） 数据存储位于中心，客户构件访问和修改共享数据。黑板是变种，感兴趣的数据变化时会通知相应的客户软件。 数据可向需要使用它的构件开放，容易增添或替换客户构件。各客户要接受共同的数据格式，客户之间的协调通常需要另外设计。
数据流体系结构 过滤器按约定格式接收数据、执行变换并产生输出，管道把数据送给后续过滤器。过滤器掌握自身输入和输出即可独立工作。 易于理解，部分处理可并行。各数据流需要协调，频繁的人机交互较难安排。课件的批序列按一条链依次处理一批数据。
调用和返回体系结构 程序构件通过调用与返回组织成控制层次。主程序／子程序逐层调用。**远程过程调用（RPC）**把被调用的构件分布到联网计算机上。 按控制层次分解功能，便于定位、修改和扩展相对独立的子功能。
面向对象体系结构 构件封装数据和施加于数据的操作，通过消息传递通信和协作。 用对象的职责和公开操作组织系统，便于封装内部状态。
层次体系结构 每层承担一定职责，为上层提供服务，并使用下层服务。 抽象层次清楚，便于增减和修改层次。采用前要判断业务的依赖关系能否合理分层。

体系结构模式与框架（第 23–24 页）

体系结构模式在特定环境、限制和约束下处理一类反复出现的应用问题。体系结构框架针对一个应用领域，将常见构件、连接和公共功能组织成可实例化的软件骨架。课件以 MFC 和 Struts 为例。选用框架后，还需要按项目要求实现具体的业务行为。

9.4 体系结构考虑要素（第 26–27 页）

要素 设计时要考虑什么
经济性 用抽象减少无用细节，把结构复杂度控制在需求所需范围内。
易见性 重要决策、依据和领域概念应能让后续设计、开发和评审人员看懂。
隔离性 划定构件边界，控制变化的影响范围。隔离过细会造成碎片化，也会让系统结构变得难以理解。
对称性 类似职责和生命周期采用均衡、一致的设计。例如账户同时有 Open() 与 Close()。
应急性 架构要能适应难以穷举的事件次序和持续时间。实时系统可通过事件驱动与灵活的自组织控制处理突发情况。

这些因素需要取舍。例如，继续隔离某个功能可以局部化变更，也会增加接口和理解成本。评估时要结合具体的质量需求和应用环境。

体系结构决策模板（第 9–10、29 页）

体系结构决策模型记录需要作出的选择、过去项目已作出的选择和支持这些选择的理由。评审或需求变更时，可以据此找到受影响的构件、约束和工作产品。

记录内容 课件中的模板字段
要解决的问题 设计问题说明要做的选择，分类标明属于数据、构件结构或集成等哪一类，相关关注点关联具体需求。
备选与前提 候选方案列出可行方案，假设写明成立前提，约束写明技术标准、可用模式或项目限制。
选择与理由 解决方案写最终选择，争论写比较方案时的依据，意义写决定对后续设计造成的影响或限制。
可追踪的记录 相关决策指出与其他决定的联系，工作产品注明在架构描述的何处体现，注释记录补充资料。

9.6 体系结构设计（第 31–39 页）

体系结构环境图（第 31–33 页）

体系结构环境图把目标系统放在中心，通过边界接口表示目标系统与外部实体怎样交互。具体角色取决于建模时选定的目标系统。

外部实体 相对目标系统的角色
上级系统 把目标系统当作更高层处理的一部分。
下级系统 被目标系统使用，为它提供需要的数据或处理能力。
同级系统 与目标系统对等交互，双方可能产生或使用相同的信息。
参与者 通过产生或消费处理信息与目标系统交互的人或设备。

体系结构原型与构件精化（第 34–37 页）

体系结构原型是对领域中关键角色和职责的高层抽象，可用少量类及其关系表达。SafeHome 原型包含控制器、结点、探测器和指示器。控制器协调警报操作，结点表达输入输出元素的集合，探测器代表摄像头等传感设备，指示器代表汽笛、闪灯等报警装置。图中探测器和指示器是结点的特化，控制器聚合结点。

课件第 34 页　SafeHome 安全功能原型的 UML 关系

形成构件体系结构时，从三个来源识别构件（第 35 页）。

  1. 应用领域。由需求分析模型中的类和业务职责导出。
  2. 基础设施域。工程上需要的内存管理、通信、数据库等公共能力。
  3. 界面领域。由环境图中的接口导出负责交互的一个或多个构件。

顶层构件要反复迭代精化。SafeHome 的外部通信管理分为图形用户界面和 Internet 接口。安全功能分为控制面板处理、探测器管理、警报处理。后续把控制面板进一步细化为键盘处理与面板显示，探测器管理引入调度器，警报处理细化为电话通信与警报（第 36–37 页）。

课件第 37 页　SafeHome 的构件体系结构精化

C/S 与 B/S（第 6、38 页）

架构 客户端与服务器怎样分工
C/S（Client/Server，客户机／服务器） 客户端发起请求、负责交互，服务器接收请求并提供数据或应用服务。典型的两层设计由专用客户端直接访问服务器，客户端还可以处理部分业务逻辑。
B/S（Browser/Server，浏览器／服务器） 以通用浏览器作为客户端。浏览器通过 Web 请求与服务器交互，服务器处理应用请求并访问所需数据，返回页面或数据供浏览器呈现。应用服务集中部署，用户通常通过浏览器访问。

B/S 是以浏览器为客户端的 C/S 形式。一个常见的 B/S 部署是浏览器 → Web／应用服务器 → 数据服务器。写答题示意时，可以用这一路径说明表现、业务处理和数据管理的分工。

课件中的 WebApp 常按多层架构组织。表现层负责用户界面，控制器根据规则协调浏览器请求和应用交互，内容层或模型层组织数据及相关业务规则（第 38 页）。

移动 App 的体系结构（第 39 页）

常见层次包括用户界面层、业务层和数据层。影响设计的七项因素是客户端类型（瘦客户端或富客户端）、支持的设备种类、连接程度、带宽需求、移动平台限制、复用与可维护程度，以及电池、内存、处理器等设备资源。比如需要间歇联网的应用，要考虑本地数据管理和恢复连接后的交互。

9.7 评估候选的体系结构设计（第 41 页）

体系结构评审是技术评审。根据性能、可扩展性等系统质量需求评估架构满足要求的能力和潜在风险，尽早发现设计问题并控制修改代价。课件指出，评审通常由软件工程团队和独立专家参与。

评审技术 怎样使用
基于经验的推理 结合已有项目的经验分析当前方案可能遇到的风险。
原型评估 用针对关键问题的小型实现验证可行性或测量性能。
情境评审 给出明确的使用、负载或变更情境，沿实际处理路径检查架构怎样响应。
检查单 按质量属性和已知风险逐项审查，核对是否覆盖重要设计问题。

例如，评估抢课高峰下的响应时间，可以设定并发访问情境，跟踪请求经过的构件，找出可能拥塞的接口，再用原型测量关键路径。

补充 从数据流图映射到软件体系结构（第 42–77 页）

变换流与事务流（第 42–50、54–56 页）

**数据流图（DFD）**沿数据流描述输入、加工、存储与输出。数据流映射根据处理职责将 DFD 转化为由构件和控制关系组成的软件结构。DFD 的箭头表示数据传递，映射结果中的上下级关系表示调用或控制。

信息流类型 识别线索 映射关注点
变换流 输入经输入流从外部表示转为内部表示，变换中心完成核心加工，再沿输出流将结果转换为外部表示。总体呈输入、变换、输出的线性处理特征。 找到输入与输出的边界，划出变换中心。不同输出可由同一次核心处理的结果生成。
事务流 外部信息转成事务。事务中心评估事务类型或条件，选择一条或若干条动作路径。 找到接收通路、集中分派的位置，以及各条动作路径。

判断时看分支的用途。若中心根据请求类型分派相应业务，按事务流考虑。若几路输出共同体现一次处理的结果，整体仍可按变换流考虑。大型系统常混合两者，课件建议以变换分析为主、事务分析为辅（第 42、55 页）。

两种映射的前三步相同。先评审基本系统模型，再细化 DFD，最后识别流类型。得到首版结构后，用设计启发式规则精化，导出接口描述和系统需要的数据结构，复查后进入详细设计（第 43、45、48 页）。

事务映射（第 44–46 页）

完成前三步后，按课件的第 4–7 步继续。

  1. 标识事务中心与动作路径。找出接收通路，分析分派条件和每条动作路径的流特征。
  2. 映射事务结构。设置总控。接收模块负责取得和预处理输入，调度模块按事务选择动作，各路径有自己的控制模块。
  3. 分解和精化。展开事务接收、分派和每条路径中的处理。路径内部可以继续作变换分析。
  4. 精化首次迭代结构。按功能独立性调整构件划分、调用关系和接口，检查每种事务是否进入对应的动作路径。

课件第 46 页　接收通路、事务中心和 A／B／C 动作路径的映射

变换映射（第 47–50、56、58–66 页）

完成前三步后，按课件的第 4–7 步继续。

  1. 分离变换中心。沿输入方向找到外部数据转换为内部表示的位置，沿输出方向找到内部结果开始转为外部表示的位置。两条边界之间是变换中心。作图时按职责和数据表示划出合理边界。
  2. 第一级分解。建立顶层主控制器，协调输入流控制器、变换流控制器和输出流控制器。顶层负责决策与协调，中间层承担部分控制和处理，底层完成主要的输入、计算和输出操作。
  3. 第二级分解。从变换中心边界沿数据流路径展开，把各加工分配到对应控制器下的模块。加工与模块可一对一映射，也可合并多个加工或进一步拆分单个加工。
  4. 精化首次迭代结构。以高内聚、低耦合为依据拆分或合并构件。保留满足功能独立性所需的模块，简化数据结构与接口，使结构易于实现、测试和维护。

课件第 49 页　x1 为总控，x2、x3、x4 分别控制输入、变换和输出

初步映射以后，每个构件都要有处理说明，写清接口、内部数据结构、功能、限制与特殊要求，如文件输入输出、硬件依赖和时间要求（第 62 页）。

SafeHome 的传感器监控案例（第 51–66 页）

  1. 第 51–54 页从环境层逐步细化到「监控传感器」的第 3 层 DFD。每个加工已有相对单一、清楚的功能，可以据此分配构件职责。
  2. 第 55–57 页判断整体为变换流。主要输入是传感器状态，还有配置数据参与处理。经过核心变换，数据可通过三路形成显示用的传感器信息、警报类型和电话语音。沿图上的两条分界读，可看到输入侧的读取与响应获取、中间的警报条件处理，以及右侧的输出。
  3. 第 58–61 页先用「监控传感器执行者」作为总控，下设传感器输入控制器、警报条件控制器和警报输出控制器，再把读取、警报条件、显示、电话等具体加工放到相应分支。
  4. 第 63–66 页按功能独立性重新组织。例如把显示格式化与生成显示合并为一个紧密职责，把部分只作转发的控制层并入处理模块，形成较简洁的结构。

练习 1

判断以下系统各采用了什么体系结构风格或子风格，并说明依据。

  1. 多个独立的分析构件读写同一份共享数据。某个构件所关心的数据变化时，系统通知该构件。

答案与解析

  1. 基于流程的建模按照数据流动的路径描述系统怎样接收输入、进行加工并产生输出。
  2. 数据流图用外部实体、加工、数据流、数据存储描述系统的逻辑功能。它可由环境层逐步细化，父子层对外数据流应保持平衡。

真题 1

答案与解析　C/S 是客户机／服务器架构。客户机响应用户操作并发出服务请求，服务器处理请求，提供共享数据或应用服务。B/S 是浏览器／服务器架构，浏览器充当客户端，经 Web 与服务器交互。Web 或应用服务器按业务规则处理请求，访问所需数据并返回结果，由浏览器呈现。B/S 是 C/S 采用浏览器作为客户端的一种形式。
